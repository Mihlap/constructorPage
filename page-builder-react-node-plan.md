# План: page builder на React + Node.js (PostgreSQL + локальные файлы → S3)

## Цель
Создать web-приложение-конструктор страниц, где:
- Редактор UI написан на React.
- Сервер (API и хранение) — Node.js.
- Состояние страницы хранится в PostgreSQL в виде JSON-схемы блоков.
- Медиа-файлы (картинки/видео/документы) сохраняются локально в проекте, а позже переключаются на S3.
- Предпросмотр страницы рендерится в браузере (без обязательной WordPress-интеграции).

## Границы MVP (минимум)
Нужны только базовые возможности:
1. Создать/открыть/сохранить “страницу-конфиг” в БД.
2. Список блоков (например: текст, изображение, контейнер/колонка, кнопка).
3. Drag-and-drop в холсте (перемещение блоков по структуре).
4. Изменение свойств выбранного блока в панели.
5. Рендер предпросмотра на основе JSON.
6. Публикация (генерация финального HTML/рендера для просмотра по URL).

## Архитектура (высокоуровнево)
### Frontend (React)
Модули:
- `editor-shell`: загрузка страницы, маршрутизация, состояние активной страницы.
- `canvas`: DOM/iframe холст, выбор/перетаскивание блоков.
- `inspector`: панель свойств выбранного блока.
- `block-palette`: каталог доступных блоков.
- `preview-renderer`: рендер JSON-схемы в “как на сайте”.

Стейт:
- Единая “модель страницы” (JSON) в памяти редактора.
- Локальные изменения → “dirty” флаг + возможность автосохранения.
- Отдельный слой преобразований: `model <-> editor view state`.

### Backend (Node.js)
Модули:
- `api`: REST endpoints (или GraphQL, но для MVP REST проще).
- `page-service`: бизнес-логика “страница/версии/публикация”.
- `render-service`: рендер предпросмотра/публикации (если нужно на сервере).
- `storage-service`: загрузка/выдача файлов (локально сегодня, S3 позже).
- `auth-service`: доступы (минимально — JWT).

Роли:
- Пользователь (создаёт/редактирует).
- В будущем — team/permissions, но MVP можно не усложнять.

## Данные (PostgreSQL)
### Минимальные таблицы
1. `users`
   - `id`, `email`, `password_hash` (если без SSO), `created_at`
2. `pages`
   - `id`, `owner_id`, `title`, `status` (draft/published/archived), `created_at`, `updated_at`
3. `page_versions` (опционально, но лучше сразу)
   - `id`, `page_id`, `version_no`, `schema_json`, `created_at`, `created_by`
4. `media_assets`
   - `id`, `owner_id`, `type` (image/video/file), `filename`, `mime_type`, `size_bytes`
   - `storage_key` (путь/ключ для локального хранения сейчас и для S3 потом)
   - `created_at`

### Модель страницы (JSON-схема блоков)
Подход: дерево/AST.
Общее:
- `root`: контейнер.
- каждый узел: `{ id, type, props, children }`
- `props` содержит только данные блока (без “UI-слоёв” редактора).

Пример (упрощённо):
```json
{
  "root": {
    "id": "root",
    "type": "container",
    "props": { "layout": "stack" },
    "children": [
      { "id": "b1", "type": "heading", "props": { "text": "Hello" }, "children": [] },
      { "id": "b2", "type": "image", "props": { "assetId": "..." }, "children": [] }
    ]
  }
}
```

## Хранилище файлов (локально сейчас)
### Интерфейс
Нужна абстракция:
- `storageService.put(file) -> asset`
- `storageService.getUrl(assetId) -> url`

Реализации:
- `LocalStorageService`: хранит в `./uploads` (или в каталоге, указанном переменной окружения).
- `S3StorageService`: позже та же схема API поверх S3.

### Практика
- В БД хранить метаданные + `storage_key`.
- Для локальных файлов выдавать через backend route вида `/api/media/:id` или проксировать статикой.

## API (контракт для MVP)
Основные endpoints:
- `POST /api/auth/register`, `POST /api/auth/login`
- `GET /api/pages/:id` (текущая версия или latest)
- `POST /api/pages` (создать draft)
- `POST /api/pages/:id/draft` (сохранить schema_json как draft-версию)
- `POST /api/pages/:id/publish` (перевод в published + закрепление версии)
- `POST /api/media` (upload)
- `GET /api/media/:id` (выдача)

Дополнительно для удобства:
- `GET /api/pages?owner=...`

## Рендеринг
### Варианты
1. Рендер только в браузере (проще MVP)
   - backend возвращает JSON → React рендерит preview и “публичную страницу”.
2. Рендер на сервере (сложнее)
   - полезно для SEO/времен загрузки, но MVP можно отложить.

Для MVP рекомендовано: (1).

## Публикация (как открыть “работу в браузере”)
Минимальный механизм:
- опубликованная страница отдаётся как frontend route:
  - например `/p/:pageSlug`
- backend хранит slug + published version.

Позже можно:
- SSR (Next.js) для SEO
- статическую генерацию.

## Drag-and-drop и выбор узлов (ключевая часть)
Нужно решить модель операций:
- Вставка нового блока из палитры.
- Перемещение существующего блока (из одного parent/position в другой).
- Удаление блока.
- Изменение props блока.

Рекомендация:
- Все операции редуцируются в “чистые трансформы JSON”.
- Редактор: “какой узел selected” — это отдельный UI state, но дерево остаётся источником истины.

## План этапов (пример на 4–6 недель)
### Этап 1 (день 1–5): каркас и контракт данных
- Скрипты запуска: dev серверы для frontend/backend.
- Построить JSON-модель страницы (типы блоков + схема).
- Минимальная БД миграции + CRUD для `pages` и `page_versions`.
- Добавить auth (минимально).

### Этап 2 (день 6–12): рендер предпросмотра
- Реализовать `preview-renderer` на основе JSON.
- 3–4 блока: heading/text/image/container.
- Убедиться, что “редактор JSON” совпадает с “preview”.

### Этап 3 (день 13–20): редактор + инспектор
- canvas: отображение дерева + выделение узла.
- inspector: редактирование props выбранного блока.
- autosave / save draft.

### Этап 4 (день 21–28): drag-and-drop
- block palette: перетаскивание в canvas.
- reorder/move внутри дерева.
- операции редактирования без поломки JSON.

### Этап 5 (день 29–35): публикация и работа через URL
- publish endpoint: закрепить версию.
- frontend route `/p/:slug`.

### Этап 6 (опционально): медиа + локальные файлы
- upload картинки → `media_assets`.
- блок `image` использует `assetId`.

## Метрики готовности (definition of done)
- Можно создать страницу, добавить блоки, изменить текст, сохранить, перезагрузить вкладку и увидеть те же блоки.
- Можно опубликовать и открыть по публичному URL.
- Медиа-файлы загружаются (хотя бы локально) и отображаются в preview.

## Риски (что может пойти не так)
- Сложность DnD для произвольного дерева (нужны чёткие операции трансформации).
- Несовпадение “редакторской модели” и “публичного рендера” (нужно единое представление).
- Модель версий и “что опубликовано” (нужно явно хранить snapshot/json версии).
